# Haze

Browser extension (WXT + Preact) that blurs, scratches out, or hides elements on
any site. `lib/` holds the logic, `entrypoints/` the extension surfaces.

## Commands

| Command | Purpose |
| --- | --- |
| `pnpm dev` / `pnpm dev:firefox` | Run with auto-reload while testing |
| `pnpm build` / `pnpm build:firefox` | Write `.output/<target>/` |
| `pnpm zip` / `pnpm zip:firefox` | Store-ready zips |
| `pnpm compile` | `tsc --noEmit` |
| `pnpm lint` | Biome |

`.output/` is a build artifact and is gitignored. **A source edit is not live in
the browser until you rebuild**, so after changing anything under `lib/` or
`entrypoints/`, run a build and reload the unpacked extension before judging
behaviour. Prefer `pnpm dev` when iterating.

## Testing selector logic without a browser

There is no test runner. To exercise `lib/selector.ts` against real markup, use
Node's TypeScript stripping plus the `linkedom` copy already in the pnpm store:

```js
// t.mjs at the repo root, then: node ./t.mjs && rm t.mjs
import { parseHTML } from "<abs path>/node_modules/.pnpm/linkedom@*/node_modules/linkedom/esm/index.js";
const { document } = parseHTML(`<html><body>…</body></html>`);
globalThis.document = document;
globalThis.CSS = { escape: (s) => s };
const m = await import("./lib/selector.ts");
```

Paste a slice of the offending page's DOM and assert both the generated selector
and its match count. Always include regression cases (hashed CSS-in-JS classes
that must stay rejected), not just the new case.

## Shipping a change ("do the thing")

Release notes are generated by GitHub from merged PR titles and labels, so the
PR title and label are the deliverable, not a hand-written changelog. The full
sequence:

1. **Audit first.** Re-read your own diff for dead logic, redundant guards,
   allocation in hot paths, and comments that explain *why* rather than restate
   the code. Fix what you find before committing.
2. **Branch** off `master`: `fix/…`, `feat/…`, or `chore/…`.
3. **Bump `version` in `package.json`.** Semver against the change, not against
   the branch prefix: a picker heuristic fix is a patch even when it also adds a
   new fallback (precedent: v2.3.2, v2.3.3).
4. **Commit** with a sentence-case subject describing the user-visible effect,
   plus a body explaining the cause. No version number in the subject; the tag
   carries it.
5. **Push and open a PR.** The title becomes the release-note line, so write it
   for a user reading the release page. Apply exactly one category label:
   `enhancement`, `bug`, `documentation`, or `chore`.
6. **Merge with `--squash`** so `master` keeps one commit per PR.
7. **Tag `v<version>` on `master` and push it.** That fires
   `.github/workflows/release.yml`, which builds, attaches both store zips, and
   publishes the release with notes generated from the PRs since the last tag.
   `.github/release.yml` maps labels to note headings.
8. **Verify** the workflow run went green and the release page reads well.

Never write release notes by hand and never create a release before the tag; the
workflow owns both.

## Conventions

- Comments explain the reason a rule exists, ideally with the concrete case that
  motivated it. Do not narrate what the next line does.
- Never use em dashes or en dashes anywhere, including code comments.
- `pnpm lint` currently reports pre-existing formatting complaints about
  hand-packed lookup tables in `lib/selector.ts`. Do not reformat them as
  drive-by work in an unrelated PR.
